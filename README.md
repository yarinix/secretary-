# Secretary Bot

Секретарь для Telegram Business: **не отвечает на каждое сообщение подряд**, а собирает пачку и отвечает один раз — только если вы сами не ответили в течение 10 минут. Если вас нет больше часа, отвечает быстро; ночью добавляет «скорее всего, уже спит, ответит утром». Управляется из Telegram Mini App на том же домене.

## Как работает

- Клиент пишет → сообщение попадает в **пачку** в БД и сдвигает её дедлайн → вы получаете одно редактируемое `📨` уведомление → через `reply_delay_minutes` минут тишины пачка уходит в каскад Gemini **одним запросом** → вы получаете `🤖` с копией ответа.
- **5 сообщений = 1 ответ.** Каждое новое сообщение отодвигает дедлайн (debounce), поэтому бот не спамит, пока собеседник дописывает.
- **Если вы ответили сами** в этом чате — пачка отменяется, уведомление помечается «✅ Вы ответили сами». Пачки в других чатах остаются.
- **Если вас не было дольше `away_minutes`** — вместо 10 минут используется короткое окно сбора `away_collect_seconds` (по умолчанию 15 сек), чтобы пачка всё равно склеилась.
- **Ночной режим**: при долгом отсутствии и текущем времени внутри `night_start`–`night_end` в system prompt добавляется инструкция (не жёсткий шаблон) — модель сама формулирует «спит, ответит утром». Ночь проверяется **в момент отправки**, а не в момент приёма.
- Обрабатываются текст, подписи, голосовые, видеосообщения (кружки) и фото. В БД хранится только `file_id` последнего вложения — файл перескачивается при доставке, поэтому вложения из середины пачки теряются (осознанное ограничение).
- Управление: **Mini App** (кнопка «Настройки» в меню бота) или команды в личке — `/business on|off`, `/business inbox on|off`, `/business notify on|off`, `/business persona <текст>`, `/business persona clear`, `/business status`.
- Логика перенесена из [ForUs](https://github.com/yarinix/ForUs-) (`tgbot/business.py`, `tgbot/llm.py`): лимит ответов в час на чат, защита от инъекций в промпте, каскад моделей.

### Умные отложенные ответы

Telegram Business **не даёт реальный online-статус**. Поэтому «вас нет в сети» = время последнего **исходящего** сообщения владельца (`last_owner_at` в БД, глобально по всем подключённым Business-чатам). Если владелец пишет вне этих чатов, метка не обновится — это ограничение API.

| Ситуация | Задержка | Режим |
|---|---|---|
| Вы недавно писали / метка ещё пустая (первый деплой) | `reply_delay_minutes` = 10 мин | `wait` |
| Вас нет дольше `away_minutes` = 60 мин | `away_collect_seconds` = 15 сек | `away` |
| `smart_replies = 0` | 0 (тот же воркер доставляет сразу) | откат к мгновенным ответам |

Пачки хранятся в `secretary_pending`, присутствие — в `secretary_meta`. Захват `claim_due()` делается атомарным `UPDATE … RETURNING` и **не удаляет пачку до подтверждённой отправки**: при сбое Gemini, сети или рестарте между SELECT и DELETE сообщение не теряется, а через 120 сек перехватывается повторно. `due_at` — wall-clock `time.time()`, **не** `monotonic()`: счётчик monotonic сбрасывается при каждом сне Render и не сравним между процессами.

Фоновый воркер (`cleanup_ctx`, тик 2 сек) подбирает дедлайны, прошедшие **во время сна сервиса**, сразу при старте до `set_webhook`. Гейты (`enabled`, права, лимит, ночь) пересчитываются из свежих настроек на доставке — за 10 минут ожидания вы могли всё поменять в Mini App.

### Каскад моделей

Тот же, что в ForUs: `gemini-3.5-flash-lite` → `gemini-3.1-flash-lite`. При `429` / исчерпании квоты бот сразу переходит к следующей модели; при временных сбоях (5xx, таймаут, обрыв связи) делает до 3 попыток на той же модели; пустой ответ считается неудачей. Список и его порядок задаётся в Mini App, дефолт — через `GEMINI_MODELS` (модели через запятую). SDK `google-genai` не нужен — запросы идут через уже имеющийся `aiohttp`.

> **Про `ANTHROPIC_API_KEY`:** Claude не подключён. Название переменной оставлено исторически (в Render уже так задано, переименовывать лень) — **в ней лежит ключ Gemini**. Можно дополнительно задать «правильное» имя `GEMINI_API_KEY`: если заданы оба, приоритет у `GEMINI_API_KEY`. Код вызовов `api.anthropic.com` удалён.

Если ключа нет вообще, бот **не отправляет собеседнику ничего**: сообщение «от лица владельца» о технической ошибке выглядело бы странно. Вы просто получите копию входящего и сможете ответить сами.

## Подключение

1. @BotFather → `/newbot`; затем Bot Settings → Business Mode → включить.
2. Нужен Telegram Premium. Настройки → Telegram для бизнеса → Чат-боты → выбрать бота, оставить право отвечать на сообщения.
3. Узнайте свой числовой ID (@userinfobot) и задайте `OWNER_ID` — **обязательно**. Бот не запустится без него: больше никто не сможет захватить управление через `/start`.
4. Задеплоить на Render, заполнить переменные. **Рекомендуется сразу задать `DATABASE_URL` и настроить внешний ping** — см. раздел ниже.
5. После первого деплоя в меню бота появится кнопка «Настройки» → Mini App.

## Mini App — управление из Telegram

Тот же aiohttp-сервер, что и вебхук, отдаёт `/app` (на проде: `https://secretary-bot-htem.onrender.com/app`). `GET /` и `GET /health` возвращают `ok`, `POST /webhook` остаётся за aiogram.

**Все функции `/business` перенесены в интерфейс**, плюс редактирование «переменных» без перезапуска: задержка **10 минут → любое число**, порог отсутствия, окно сбора пачки, границы ночи, текст ночной подсказки, лимит ответов в час, размер истории, лимит persona, имя владельца, часовой пояс, игнорируемые ID, порядок моделей каскада.

| Что | Где меняется | Когда применяется |
|---|---|---|
| Автоответы, копии входящих/ответов, persona | UI → таблица `settings` | сразу, к следующему сообщению |
| Задержка, отсутствие, сбор пачки, ночь | UI → `settings` | сразу, **в том числе к уже ждущим пачкам** (гейты пересчитываются на доставке) |
| История, лимит persona, имя, часовой пояс, игнорируемые ID | UI → `settings` | сразу |
| Порядок моделей каскада | UI → `settings` | сразу (объект `GeminiCascade` создаётся на вызов) |
| `BOT_TOKEN`, `OWNER_ID`, `WEBHOOK_SECRET`, `DATABASE_URL`, `PORT` | только дашборд Render | после рестарта |
| Ключ Gemini (`ANTHROPIC_API_KEY` / `GEMINI_API_KEY`) | только дашборд Render | после рестарта |
| Активное хранилище (`STORAGE_BACKEND`) | читается в UI, раздел «Системное» | — |

В шапке приложения показывается живой статус: число пачек в очереди, сколько минут вас нет, когда ждать ближайший ответ и «🌙 сейчас ночь». `status_provider()` синхронный (веб-слой отклоняет awaitable) и читает кэш, который воркер обновляет на каждом тике. Наружу уходят только поля из явного белого списка `STATUS_KEYS`.

Ключ Gemini **не показывается и не меняется** в UI — только индикатор «задан / не задан». `DATABASE_URL` (DSN с паролем) в UI не отдаётся вообще: вместо него приходит готовая строка «Postgres (устойчиво)» или «SQLite (временный — сбросится при рестарте)». Системные значения приходят в `/api/state` замаскированными и никогда не принимаются в `/api/settings`.

**Безопасность.** Каждый запрос к `/api/*` подписан `initData`: `secret = HMAC_SHA256("WebAppData", BOT_TOKEN)`, подпись — HMAC от отсортированного `data_check_string`, сравнение через `hmac.compare_digest`. Дополнительно проверяются свежесть `auth_date` (TTL 1 час, отсекаются будущие даты) и `OWNER_ID`. `initDataUnsafe` не используется. Подделанная подпись → `401`, чужой пользователь → `403`, невалидные поля → `400` с ошибками по конкретным ключам (сохранение all-or-nothing). Ответы идут с `Cache-Control: no-store`, тело запроса ограничено 64 КБ, секреты и `initData` не логируются и не сериализуются.

**Роуты:** `GET /`, `GET /health`, `GET /app`, `GET /static/{app.css,app.js}`, `POST /api/state`, `POST /api/settings`, `POST /api/test-ai`, `POST /webhook`. CORS не нужен — same-origin.

Ручная проверка после деплоя: открыть Mini App → поставить «Ждать тишины» **10 → 1** → написать в чат 5 сообщений подряд → через ~1 минуту приходит **ровно один** ответ, а в шапке «в очереди: 1» → 0. Затем ответить самому до дедлайна — автоответ отменяется.

## Устойчивость на Render Free

На бесплатном плане есть два независимых эффекта, которые выглядят как «сообщения не будят сервер» и «настройки откатываются»:

1. **Сон и холодный старт.** Render усыпляет Free-сервис через 15 минут без входящего трафика и поднимает его ≈1 минуту по следующему HTTP-запросу. POST от Telegram формально будит сервис, но Telegram не ждёт минуту: при неуспешном вебхуке он повторяет попытку «разумное число раз» и сдаётся. Раньше вдобавок `set_webhook(drop_pending_updates=True)` при каждом старте **сам вычищал** ещё не доставленную очередь.
2. **Эфемерный диск.** Render прямо называет `local SQLite databases`: все изменения файловой системы теряются при redeploy, restart **и spin down**. Persistent disk доступен только платным сервисам. Поэтому `secretary.db` с настройками из UI неизбежно откатывался к env-дефолтам.

Что сделано в коде:

| Мера | Файл | Эффект |
|---|---|---|
| `drop_pending_updates=False` | `main.py` | старт больше не удаляет очередь Telegram |
| Явный `handle_in_background=True` | `main.py` | вебхук сразу отвечает `200`, Gemini считается в фоне |
| Дедупликация `update_id` | `dedup.py` + `secretary_meta` | повторная доставка не даёт второго автоответа даже **после рестарта** (in-memory guard пустеет, поэтому последний `update_id` продублирован в БД) |
| `seen_ids` в пачке | `storage.py` / `pg_storage.py` | тот же `message_id` не сдвигает дедлайн повторно |
| `GET /health` без БД и авторизации | `webapp.py` | внешний мониторинг будит сервис, не ломаясь на недоступном Postgres |
| `PgStorage` по `DATABASE_URL` | `pg_storage.py` | настройки, история, подключения **и пачки** живут вне эфемерного диска |
| Фоновый воркер пачек | `main.py` | подбирает дедлайны, прошедшие за время сна, при старте и каждые 2 сек |

### Шаг 1. Внешний Postgres

Подойдёт любой постоянно живущий Postgres — [Supabase](https://supabase.com/) или [Neon](https://neon.tech/) (бесплатные тары не истекают). **Free Render Postgres не годится**: он удаляется через 30 дней после создания, а Free Key Value держит данные только в памяти.

1. Создайте проект и скопируйте DSN вида `postgresql://postgres.[ref]:PASSWORD@aws-0-[region].pooler.supabase.com:5432/postgres?sslmode=require`.
   - В окне **Connect** берите **Session pooler** (порт **5432**, IPv4), а не Transaction pooler (6543) и не Direct connection (`db.*.supabase.co` — он IPv6 и с Render без IPv4 Add-On не соединится). Драйвер всё равно отключает prepared statements, поэтому 6543 тоже заработает, но 5432 надёжнее.
   - Пароль задайте **только латиницей и цифрами**: символы `@ : / # ?` в DSN пришлось бы процент-кодировать, иначе `psycopg` не разберёт строку.
   - Поле «Relative path to the directory containing your supabase/ folder» (Working directory) относится к GitHub-интеграции и CLI-миграциям: снимите привязку к GitHub или впишите `.`. Папку `supabase/` создавать не надо — таблицы бот создаёт сам.
2. В Render → ваш сервис → **Environment** добавьте `DATABASE_URL` со значением DSN и сохраните (деплой перезапустится).
3. Таблицы `secretary_settings`, `secretary_history`, `secretary_connections`, **`secretary_pending`**, **`secretary_meta`** и индексы создаются автоматически при старте — миграции не нужны. Разовая очистка мёртвой строки после обновления: `DELETE FROM secretary_settings WHERE key='takeover_minutes';` (старая пауза удалена из кода и UI, но строка в БД просто игнорируется).
4. Откройте Mini App → «Системное» → строка **Хранилище настроек** должна показывать `Postgres (устойчиво)`.

> ⚠️ `render.yaml` тоже обновлён, но он применяется только если сервис создан как **Blueprint**. Прод сейчас отвечает `Python/3.14`, хотя в файле указано `3.11.9` — значит сервис, скорее всего, создан вручную и переменную нужно добавить именно в Dashboard. Проверьте оба места.

Env-переменные (`BUSINESS_REPLY_DELAY_MINUTES`, `OWNER_NAME`, …) остаются **дефолтами для пустой базы**: как только вы что-то сохранили в Mini App, источник истины — Postgres. Если DSN неверный, сервис не стартует с понятным сообщением; сам DSN и текст ошибки в логи не пишутся.

Без `DATABASE_URL` всё работает по-старому на SQLite (обратная совместимость), но в лог пишется предупреждение, а UI показывает «SQLite (временный)».

### Шаг 2. Внешний ping, чтобы сервис не засыпал

Настройте любой внешний мониторинг на `GET https://secretary-bot-htem.onrender.com/health` с интервалом **5–10 минут** (обязательно меньше 15). Например [cron-job.org](https://cron-job.org/), UptimeRobot, Better Stack или обычный cron на своём хосте:

```bash
*/10 * * * * curl -fsS --max-time 30 https://secretary-bot-htem.onrender.com/health > /dev/null
```

`/health` не трогает Postgres и не требует `initData`, поэтому отвечает `200 ok` даже если БД временно недоступна. `healthCheckPath: /` в `render.yaml` — это проверка от самой платформы и **не является** внешним трафиком: на неё как на keep-alive полагаться нельзя.

> **Для отложенных ответов ping обязателен вдвойне.** Окно ожидания 10 минут **меньше** порога сна Render (15 минут): без внешнего трафика сервис уснёт раньше, чем пачка дозреет, и её подберёт только холодный старт (≈1 минута) при следующем сообщении. С ping раз в 5–10 минут воркер крутится постоянно и доставляет пачки точно в срок.

### ⚠️ Лимит 750 бесплатных часов

Render даёт **750 free instance hours на рабочее пространство в месяц**, и сервис тратит их всё время, пока запущен. Круглосуточный ping — это ≈744 часа в месяц из 750: лимит почти исчерпан, и в конце месяца Free-сервисы могут быть приостановлены до его сброса. Это ограничение платформы, обойти кодом нельзя. Если столкнётесь с этим (или устанете от двух внешних зависимостей), апгрейд до Starter (~$7/мес) решает **обе проблемы сразу**: платный сервис не засыпает и к нему можно примонтировать persistent disk (`DB_PATH=/var/data/secretary.db`), отказавшись и от Postgres, и от ping.

Отдельно: **Free-проект Supabase приостанавливается после 7 дней низкой активности** ([Project Pausing](https://supabase.com/docs/guides/platform/project-pausing)). Пока бот отвечает на сообщения, он ежедневно читает и пишет БД — этого достаточно. Но если оставить проект без трафика на неделю, его придётся восстановить кнопкой **Resume project** в дашборде (данные сохраняются, окно восстановления — 1 год).

### Как проверить

1. `curl -i https://secretary-bot-htem.onrender.com/health` → `200 ok`.
2. Mini App → «Системное» → `Postgres (устойчиво)`.
3. Поменять «Ждать тишины» **10 → 1**, сохранить, сделать **Manual Deploy / Restart** в Render, снова открыть Mini App → значение осталось `1`.
4. Написать 5 сообщений подряд → ровно 1 ответ; ответить самому до дедлайна → автоответ отменён.
5. Оставить сервис на 20+ минут при работающем ping, написать в чат — сообщение приходит без «холодного» ожидания.

## Переменные окружения

| Переменная | Обязательная | Описание |
|---|---|---|
| `BOT_TOKEN` | да | токен от @BotFather |
| `OWNER_ID` | **да** | ваш числовой Telegram ID |
| `DATABASE_URL` | **рекомендуется** | DSN внешнего Postgres; без него — эфемерный SQLite |
| `ANTHROPIC_API_KEY` | нет | **ключ Gemini** (историческое название, см. выше) |
| `GEMINI_API_KEY` | нет | «правильный» алиас; приоритет над `ANTHROPIC_API_KEY` |
| `GEMINI_MODELS` | нет | дефолт каскада через запятую; переопределяется в UI |
| `WEBHOOK_SECRET` | нет | секрет вебхука; если не задан, берётся хэш от `BOT_TOKEN` (не «change-me») |
| `WEBHOOK_BASE_URL` | нет | базовый URL вебхука; если не задан, используется автоматический `RENDER_EXTERNAL_URL` |
| `WEBAPP_URL` | нет | полный URL Mini App (с `/app`); если не задан, берётся `BASE_URL + /app` |
| `OWNER_NAME` | нет | как зовут владельца в промпте (дефолт для UI) |
| `BOT_TIMEZONE` | нет | часовой пояс (дефолт для UI), по умолчанию `Asia/Omsk` |
| `BUSINESS_SMART_REPLIES` | нет | `0` = отвечать сразу (откат), по умолчанию `1` |
| `BUSINESS_REPLY_DELAY_MINUTES` | нет | ждать тишины, 10 (дефолт для UI) |
| `BUSINESS_AWAY_MINUTES` | нет | считать отсутствием, 60 (дефолт для UI) |
| `BUSINESS_AWAY_COLLECT_SECONDS` | нет | сбор пачки при отсутствии, 15 сек (дефолт для UI) |
| `BOT_NIGHT_ENABLED` | нет | ночной режим, по умолчанию `1` |
| `BOT_NIGHT_START` / `BOT_NIGHT_END` | нет | границы ночи `HH:MM`, `01:00` / `08:00` |
| `BOT_NIGHT_HINT` | нет | пожелание к ночной формулировке (дефолт для UI) |
| `BUSINESS_MAX_REPLIES_PER_HOUR` | нет | лимит ответов на чат, 20 (дефолт для UI) |
| `BUSINESS_IGNORE_IDS` | нет | ID через запятую (дефолт для UI) |
| `DB_PATH` | нет | путь к SQLite, по умолчанию `secretary.db` (игнорируется при `DATABASE_URL`) |
| `PORT` | нет | порт, по умолчанию 10000 |

Все пользовательские переменные объявлены в `render.yaml`; `WEBHOOK_SECRET` генерируется Render автоматически. `RENDER_EXTERNAL_URL` Render подставляет сам — если его не окажется, бот поднимется, но запишет предупреждение в лог и не получит обновления (поллинг-фолбэка нет). Если сервис создан вручную, а не из Blueprint, добавьте `DATABASE_URL` в Dashboard (см. раздел выше).

Тесты покрывают чистые функции, сборку `contents` для Gemini, SQLite (WAL, атомарная запись, **debounce пачек, `claim_due`, stale-перехват, дедуп `message_id`**), схему настроек и границы валидации (включая новый тип `clock`), политику задержек и ночи, подпись `initData`, HTTP-роуты Mini App (401/403/400/413/415, отсутствие утечек секретов), `/health`, дедупликацию `update_id` и SQL-контракт `PgStorage` на подставном соединении. Реальный Postgres, сеть и `BOT_TOKEN` тестам не нужны.

Структура: `config.py` (валидация окружения), `helpers.py` (чистые функции), `reply_policy.py` (политика дедлайнов и ночи), `pending_codec.py` (общий формат строк пачек), `storage.py` (SQLite + RLock/WAL + пачки), `pg_storage.py` (внешний Postgres + пачки), `dedup.py` (дедуп `update_id`), `llm.py` (каскад Gemini), `app_settings.py` (схема настроек), `miniapp_auth.py` (`initData`), `webapp.py` (HTTP-роуты и `/health`), `web/` (HTML/CSS/JS Mini App), `main.py` (aiogram-обработчики, фоновый воркер, webhook, выбор бэкенда, сборка приложения).
